# 项目协作规范

## 范围与事实来源

- 默认使用中文交流、文档字符串和必要注释。代码标识符和提交标题使用清晰的英文。
- 后续业务代码、测试、脚本和文档集中在本目录，随任务逐步增加，不提前建立无用途的框架或空目录。
- 本目录与 CARLA 共用一个 Git 仓库。已有 sensor 集成源码保留原位置；确需修复时修改源文件，不修改生成头文件、依赖安装副本或其他构建产物。
- 需求以用户最新确认内容和 [设计概览](docs/planning/project-overview.md) 为准；进度以 [GitHub Project](https://github.com/users/ACienZ/projects/9) 为准。[TODO](TODO.md) 是带日期的摘要，不是另一个独立看板。
- 历史对话、旧脚本和旧实验用于解释背景，不能据此宣布当前接口或当前任务已验收。读取不到的远端状态明确标为未知。
- 本文件只维护稳定规则，不重复维护动态任务进度。

## 工作方式与授权

- 开始前核对 TODO、对应 Issue、Project 状态、当前分支、未提交修改和远端状态；保留已有修改及未跟踪文件。
- 先确认目标、边界和可验证的验收标准，再实施业务代码。每次推进一个可独立审阅的子任务，不顺手扩大范围。
- 用户已授权助手管理 carla-audio 全部历史和未来任务的标签、Priority、Size、状态及验收记录，以及已确认范围内的分支、提交、推送和 PR。普通操作不重复请求业务确认。
- 授权范围是 carla-audio，不扩展到账号下其他项目；具体任务要求“仅提交 PR”时停在 PR 创建完成。PR 合并服从当前任务的交付边界与验证结果。
- 新的技术选择、依赖、接口变化和范围变化先说明用途及影响，再与用户讨论。发布、CD 和破坏性操作不因拥有仓库权限而自动纳入任务。
- 已确认的需求和设计写入 `docs/planning/`；区分已确认、待决和历史方案。完成当前子任务后再进入下一项。

## Issue 与 Project

- 一个任务应有目标、范围、前置依赖、验收标准、验证方法、Issue 和对应分支。先查询已有任务，避免重复创建。
- 新建任务加入现有 Project，并填写标签、Priority、Size。已有完成项也纳入分类和估计；删除的任务不自行重建。
- Labels 表示任务类型，Priority、Size 是 Project 字段，分别维护；不要用标签代替字段。
- 复用仓库现有标签；`maintenance` 用于仓库及开发流程维护。合理的已有标签应保留。

| 字段 | 约定 |
| --- | --- |
| P0 | 当前工作被阻塞、需要优先解决的紧急问题 |
| P1 | 当前 Demo 主线和实现它所需的任务 |
| P2 | 辅助维护、后续研究或当前范围之外的事项 |
| XS | 单点调整 |
| S | 范围清楚的小任务 |
| M | 需要实现、整理及验证的模块任务 |
| L | 跨模块或需要较多研究的任务 |
| XL | 需要拆分的整体任务 |

Size 是相对工作量，不是数据集大小或承诺工期。历史项按原任务范围回顾性估计，不表示当时实际投入；attention 项估计的是当前条目的整理或研究，不是未确认的完整实现。父任务的整体估计不与子任务重复累计。

| Project Status | 使用方式 |
| --- | --- |
| Details that Need Attention | 备忘、约束或后续问题；不会因为填了优先级和工作量就进入实施计划 |
| TODO | 尚未开始或尚未正式交付的任务 |
| In progress | 已开始实施；提交 PR 等待合并时仍保留此状态 |
| Done | 对应交付已合并且验收完成 |
| Abandoned | 明确取消或不再推进的任务，保留原因及历史关联 |

Issue 的 open/closed 与 Project Status 是不同信息。整理字段时不得顺手改变状态；只有核对验收依据后才更新进度。远端修改后回读核验，不只依赖命令退出成功。

## 分支、提交与 PR

- 当前 Demo 使用“任务分支 → `7-audio-gen-demo/main` → `main`”。Demo 任务默认从最新远端集成分支创建，PR 也以该集成分支为目标。
- 新任务分支一律命名为 `<issue编号>-<任务描述>`，不加 `codex/`。这覆盖通用工具或旧文档中的默认前缀；不为统一名称而重命名已有分支。
- 不改写历史提交；不擅自强推、删除分支或更改仓库保护规则。同步时保留其他人的工作。
- 提交前阅读完整 diff，精确暂存本任务文件，再阅读 `git diff --cached` 并运行 `git diff --cached --check`。空白检查不能代替审阅。
- 提交标题使用 `type: description(#编号)`，如 `docs: establish dataset project foundation(#19)`。type 按实际改动选择 `feat`、`fix`、`test`、`docs`、`ci`、`chore` 等，不全部使用 chore。
- 提交中的编号关联当前 Issue；PR 正文另给 Issue 链接。Codex 协助提交保留 `Co-authored-by: Codex <noreply@openai.com>`。
- PR 说明问题、最终变化、实际验证及未完成边界，不复制聊天过程。使用符合当前任务的标题，不沿用旧 PR 的笼统描述。
- PR 指向非默认分支时，不依赖关闭关键词自动关闭 Issue；合并且验收完成后核对 Issue 和 Project 状态。
- 提交 PR 后记录其链接。当前任务要求停在创建 PR 时，不提前合并或把任务标记 Done。

## 实现、注释与环境

- 使用简单、职责清楚的实现，不增加未经确认的功能或依赖。
- 重要类、函数和测试说明它在解决什么问题、为什么这样做、输入输出、副作用、调用顺序以及失败时怎样处理。
- 涉及帧、时间、数据缺失等逻辑时，解释数据来自哪里、如何匹配、哪些值是测量值、哪些是估算值；避免机械复述每一行代码。
- 沿用 Conda `carla` 环境。构建 PythonAPI 和运行客户端使用同一解释器；具体环境与命令见 [开发指南](docs/development.md)。不直接套用其他项目的 uv 配置。
- 原始测量与后处理结果分开保存。后续运行数据、WAV、缓存、日志和本地配置应设置输出位置与忽略规则；在相应实现任务中落实，不混入普通源码提交。
- 凭证不写入仓库、命令输出或 PR；提交配置示例而非真实凭证。

## 验证与交付

- 检查强度与改动匹配：文档检查链接、命令、路径、接口和差异；业务变化验证相应正常、边界与失败行为。
- 区分静态检查、导入检查、单元测试、CARLA 运行时测试、CI 和发布验证。导入成功不代表服务端已启动或端到端通过。
- 用户提供的历史运行输出标明来源，不冒充本轮重跑；测试曾通过也不等于测试脚本已经提交并可复现。
- 本轮任务通过必要检查后不无理由重复全量构建。未执行的检查及剩余限制明确说明。
- 交付时说明改了什么、验证了什么、未完成什么，给出 Issue/PR 和文档入口。同步进度摘要及远端状态，但不把创建 PR 当作合并。
