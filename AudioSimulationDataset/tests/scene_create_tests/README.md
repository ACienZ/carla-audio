# 救护车匀速接近与距离采集

对应 [Issue #8](https://github.com/ACienZ/carla-audio/issues/8)。[create_scene.py](create_scene.py) 基于 [#10 静态接收](../audio_source_tests/README.md)，保持 ego 静止，将救护车沿 ego 朝向的反方向摆放，再逐帧接近，保存 sensor 的帧号、仿真时间戳和距离，供 #11 离线生成声音。

## 运行

按 [开发指南](../../docs/development.md) 启动本项目的服务端，使用 UE 编辑器时先点击 Play。确保没有其他客户端推进世界，再运行：

```bash
conda activate carla
cd /home/test/carla-0.9.16
python AudioSimulationDataset/tests/scene_create_tests/create_scene.py
```

脚本不切换地图、不清理已有车辆。请先为当前地图选择有足够长度的直路出生点，在脚本顶部修改 `SPAWN_POINT_INDEX`；默认索引 0 只是入口，不保证适合当前地图。创建位置被占用会直接报错，不自动换点或重试。

## 参数与执行顺序

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `INITIAL_DISTANCE_METERS` | 30.0 | 初始 Actor 原点间距，米 |
| `APPROACH_SPEED_MPS` | 2.0 | 每个仿真秒接近的米数 |
| `DURATION_SECONDS` | 10.0 | 首末测量之间的目标仿真时长 |
| `FIXED_DELTA_SECONDS` | 0.05 | 每个世界帧的仿真时间，秒 |

连接参数、超时、车辆类型也集中在顶部。修改时长时保持其为步长的整数倍；修改距离、速度或时长时，保证最终距离为正且车辆车身仍有间隔。当前默认终点间距为 10 米，不让救护车穿过 ego。

执行顺序：保存世界设置 → 启用同步模式 → 创建两车与 sensor → 监听 → 按步数设置救护车位置 → tick → 取事件并核对帧号 → 保存 JSON → 清理和恢复设置。

两车都关闭物理模拟。救护车每步使用 `set_location()` 设置位置，保持朝向不变；默认每步接近 0.1 米。距离根据步数计算，而不是每次在上一步位置上相加。先记录初始距离，再执行 200 次移动，共 201 条记录，首末测量相隔 10 个仿真秒。首次采样本身也需要一次 tick，因此脚本总共推进 201 帧。

这是沿固定直线的位置控制，不是物理匀速驾驶；不搜索车道、跟随弯道或保证同车道。需要在选定直路上观察摆放与运动是否符合场景要求。本次不实现自动驾驶、地图天气配置、相机或音频生成。

## JSON 与 #11 的衔接

正常采集完成后输出 `data/<运行时间>.json`，路径相对脚本定位，与启动命令的工作目录无关。文件名含微秒，独占创建避免覆盖。`data/` 已整体加入本目录的 Git 忽略规则。

JSON 仅包含 `measurements`，按采集顺序保存 `frame`、`timestamp`、`distance_m`。这三个值都来自 `AudioSourceEvent`，保存时不截断精度。`distance_m` 为两车 Actor 原点的三维距离，不是保险杠间距，也不是客户端的计划距离。按用户审阅意见，本次不保存地图、车辆和运动参数等配置元数据；原始记录足以供 #11 读取，但无法仅凭该文件还原运行配置。

`timestamp` 保留世界原始仿真秒数。#11 读取后减去首条时间戳，即得到从 0 到约 10 秒的音频时间轴；本模块不插值、不生成逐帧音频或连续 WAV。采集格式是当前 Demo 的最小接口，不替代正式 DatasetGenerator 的数据设计。

可以独立读取刚生成的文件核对内容，将下面路径替换为脚本打印的实际路径：

```python
import json
from pathlib import Path

data_path = Path("AudioSimulationDataset/tests/scene_create_tests/data/<运行时间>.json")
data = json.loads(data_path.read_text(encoding="utf-8"))
measurements = data["measurements"]
print("记录数：", len(measurements))
print("首条：", measurements[0])
print("末条：", measurements[-1])
print("首末时间差：", measurements[-1]["timestamp"] - measurements[0]["timestamp"])
```

## 错误与清理

取队列时最多等待 5 个现实秒，超时直接抛出 `queue.Empty`；收到事件的帧号与 tick 不一致时直接报错。本模块不重试、不补帧、不用计划值替代缺失测量。同步模式需要只有一个客户端推进世界。

单个 `event` 只代表一帧，队列可以存放多个事件，`get()` 每次取出最早入队的一个。本脚本是“tick 一次 → 等待并取出事件 → 核对 → 下一次 tick”；网络迟到但仍在超时内的当前帧可正常接收。该判断只检查采样帧号，不检查到达时间。若当前帧始终没有事件，会先在 `get()` 超时；若队列中取到旧帧或其他帧，则在帧号判断处失败。这里刻意采用直接失败的最小策略，不支持积压数据处理、跳帧或相机延迟多帧的采集。

只有完整接收后才开始写 JSON，采集超时或中断不会输出不完整的测量文件。文件写入期间遇到中断、磁盘或权限错误仍可能留下不完整文件；本轮不增加原子写入或恢复逻辑，不应将该文件用于 #11。

正常结束、接收失败或 Ctrl+C 都会进入同一处 `finally`：停止 sensor、逆序销毁本次对象、恢复原始 WorldSettings。恢复设置不回退仿真时间，也不还原世界里其他对象的运行状态。服务端断开时清理调用本身仍可能失败，不增加嵌套恢复逻辑。

## 验证标准与记录

默认参数下检查：201 条记录；帧号连续；相邻时间戳差约 0.05 秒；首末时间差约 10 秒；距离由约 30 米减至约 10 米。第 i 条（从 0 开始）的计划距离为 `30 - 2 * i * 0.05` 米，sensor 距离与它的差以 0.01 米作初步核对容差。计划值仅为控制预期，不是同帧快照的独立距离真值。

运行时可观察 ego 是否保持静止、运动方向是否正确，并核对清理后本次对象消失、世界设置恢复，再次运行确认出生点可复用。时间差使用浮点容差比较，不要求浮点数逐位相等。以下区分本次已有证据与尚未独立验证的部分。
